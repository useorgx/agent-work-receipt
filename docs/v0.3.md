# Agent Work Receipt v0.3

v0.3 is v0.2 plus optional fields. Every v0.1 and v0.2 field keeps its meaning,
v0.1 and v0.2 receipts stay valid under their own `schema_version`, and a
producer moves to v0.3 by changing `schema_version` to `agent-work-receipt/v0.3`
and adding only the fields it can fill honestly. The schema
(`schema/agent-work-receipt.v0.3.schema.json`, `$id`
`https://useorgx.com/schemas/agent-work-receipt/v0.3/schema.json`) is generated
from the v0.2 schema by `scripts/build-v0.3-schema.mjs`, so the shared parts
cannot drift.

v0.2 says what was done and what was checked. v0.3 says **how strongly** each
claim is backed: who saw an action happen, who checked the result and whether
they were the same party that did the work, and whether anyone looked at the
outcome in the world.

| Question a reader asks | v0.2 | v0.3 |
| --- | --- | --- |
| How far does this receipt's claim go? | Not stated. | `outcome.claim_level`, on an ordered ladder the validator enforces. |
| Did anyone besides the agent see this action or effect? | Not stated. | `actions[].coverage` and `outcome.effects[].coverage`: `enforced`, `observed_only`, `outside_coverage`. |
| Which effects did the work have, and how are they known? | `outcome.observed_effects` strings. | `outcome.effects[]` with coverage, actions, and evidence. |
| Who produced each check verdict? Was it the agent grading itself? | One `verification.verifier` for the whole receipt. | `verification.checks[].verifier`: identity, model family, evidence source. |
| Is this the same trace the producer saw? | `lineage.trace_id` only. | `lineage.trace_commitments[]`: a SHA-256 Merkle root over the trace spans, by reference. |

## Fields

All are optional. Exact names:

- `outcome.claim_level`: one of `asserted`, `executed`, `observed`, `checked`,
  `accepted`, `outcome_observed`.
- `outcome.effects[]`: `{ id, summary, coverage, evidence_ids, target_ref?, action_ids?, observed_at? }`.
- `actions[].coverage`: one of `enforced`, `observed_only`, `outside_coverage`.
- `verification.checks[].verifier`: `{ actor, evidence_source, model_family? }`,
  where `evidence_source` is one of `system_of_record`, `independent_execution`,
  `actor_supplied`, `human_judgment`, `other`.
- `intent.consequential`: boolean, default `true`.
- `actor.model.family` (and any `model.family`): model family, for example
  `claude`, `gpt`, `gemini`, `llama`.
- `lineage.trace_commitments[]`: `{ trace_id, algorithm: "sha256", root, construction?: "awr-trace-merkle/v1", leaf_count?, trace_ref?, committed_at? }`.

### Coverage

| Value | Meaning |
| --- | --- |
| `enforced` | The action or effect passed through a control point that could have blocked it, and that control point recorded it (a policy gateway, a protected-branch rule, an MCP proxy that decides). |
| `observed_only` | A system other than the actor recorded it but could not have blocked it (a VCS log, an audit trail, a tracer). |
| `outside_coverage` | Known only from the actor's own report. |

Leaving `coverage` out makes no claim.

## Claim levels

The ladder is ordered, weakest first:

`asserted` < `executed` < `observed` < `checked` < `accepted` < `outcome_observed`

Claiming a level claims every level below it. The validator therefore requires
the supporting fields of **every level up to and including** the one claimed.
Leaving `claim_level` out makes no claim, and no claim-level rule applies.

| Level | The receipt must contain | Issue when it does not |
| --- | --- | --- |
| `asserted` | Nothing beyond a valid receipt. | — |
| `executed` | At least one action with status `completed`. | `semantic.claim_level_unsupported` at `/actions` |
| `observed` | At least one `outcome.effects[]` entry with coverage `enforced` or `observed_only` and at least one evidence id. | `semantic.claim_level_unsupported` at `/outcome/effects` |
| `checked` | `verification.status` `passed` or `partial`, and at least one **qualifying check**: status `passed`, at least one evidence id, a verifier, and — for consequential work — a verifier that is not the receipt actor. | `semantic.claim_level_unsupported` at `/verification/status` or `/verification/checks`; `semantic.self_verification` when the only passed checks were verified by the actor |
| `accepted` | `outcome.acceptance` with status `accepted`, `occurred_at`, and an `actor` of type `human` who is not the receipt actor. | `semantic.claim_level_unsupported` at `/outcome/acceptance`; `semantic.self_acceptance` at `/outcome/acceptance/actor` |
| `outcome_observed` | At least one `outcome.metrics[]` entry with `observed_at` and an evidence id, or one `outcome.expected_results[]` entry with status `within` or `outside` and an evidence id. | `semantic.claim_level_unsupported` at `/outcome/metrics` |

`highestSupportedAgentWorkClaimLevel(receipt)` returns the strongest level a
receipt's fields support, whatever it claims. Hosts can use it to re-derive a
claim; producers can use it to choose one. `agentWorkClaimLevelIssues(receipt,
level)` lists what is missing for a given level.

### Self-verification

A check's **verifier** is `verification.checks[i].verifier.actor` when present,
otherwise `verification.verifier`. Two actors are the **same identity** when
their `type` and `id` are both equal; `display_name`, `model`, and `runtime` are
ignored, so renaming an agent does not make it independent.

Work is **consequential** unless the producer sets `intent.consequential` to
`false`. That default is deliberate: a receipt must opt out, in a signed field,
before a self-check can count.

**Rule:** for consequential work, a check whose verifier is the same identity
as the receipt `actor` cannot support `checked`. It may still be recorded, and
it still counts toward `verification.status`; it just is not the independent
check the claim needs. If every passed check is self-verified, the validator
reports `semantic.self_verification` at that check's
`/verification/checks/{i}/verifier/actor` (or at `/verification/verifier` when
the check has no verifier of its own).

The validator enforces only identity. `model_family` and `evidence_source` are
recorded so a host can apply stricter policy: for example, treating a reviewer of
the same model family as correlated, or refusing `actor_supplied` evidence for
high-risk work. Acceptance by the party that did the work is covered by the
`self_acceptance` rule above.

## Trace commitments (awr-trace-merkle/v1)

A trace commitment lets a receipt bind the exact trace it was produced from
without carrying any span. The spans stay with their owner (`trace_ref`); anyone
who later obtains them can recompute the root and compare.

For spans `s_1 … s_n`, each a JSON object (for example an OTLP/JSON span):

1. `leaf_i = SHA-256(0x00 || UTF-8(RFC 8785 canonical JSON of s_i))`
2. Sort the leaves ascending by byte value. Duplicates are kept. The root
   therefore does not depend on the order the spans were exported in.
3. `root` is the RFC 6962 Merkle tree hash of the sorted leaves:
   `MTH([]) = SHA-256("")`, `MTH([h]) = h`, and for `n > 1`
   `MTH(h[0:n]) = SHA-256(0x01 || MTH(h[0:k]) || MTH(h[k:n]))` with `k` the
   largest power of two less than `n`.
4. Encode `root` as lowercase hex.

`algorithm` is always `sha256`. `construction` absent means
`awr-trace-merkle/v1`. When present, `leaf_count` must equal the number of spans.
The validator checks the shape and that each `trace_id` is committed at most
once; it cannot check the root without the spans. The SDK exports
`computeAgentWorkTraceCommitmentRoot`, `createAgentWorkTraceCommitment`, and
`verifyAgentWorkTraceCommitment`.

## Signature verification

The signature profile is unchanged (`agent-work-receipt-signature/v0.1`). The
SDK can now verify Ed25519 signatures itself, with Web Crypto, given a key
resolver:

```ts
import {
  createAgentWorkKeyResolver,
  verifyAgentWorkReceiptIntegrity,
} from '@useorgx/agent-work-receipt';

const report = await verifyAgentWorkReceiptIntegrity(receipt, {
  resolve_public_key: createAgentWorkKeyResolver({ keys: jwks }),
});
```

A resolver returns a key (raw 32 bytes, base64url or hex string, an
`OKP`/`Ed25519` JWK, or a `CryptoKey`) or `null`/`undefined` when it has none.
No key leaves the signature `not_checked`; an unusable key or a throwing resolver
reports `error`. The existing `verify_signature` callback still works and takes
precedence when both are given. Signer trust remains a separate decision
(`evaluate_signer_trust`). On Node.js 20, Web Crypto Ed25519 prints an
`ExperimentalWarning`; Node.js 22 and later do not.

## Offline verifier

```sh
npx awr-verify receipt.json --key <base64url | hex | key file>
npx awr-verify receipt.json --keys jwks.json --strict --json
```

`--key` applies to every signature and accepts a raw key inline, or a file with
a raw key, a JWK, or an SPKI PEM. `--keys` matches signatures to JWKS entries by
`kid`. The verifier prints validation issues, the highest supported claim level,
the computed content hash and its state, and each signature's state.

| Exit | Meaning |
| --- | --- |
| 0 | Valid; no integrity failure. |
| 1 | Unreadable, not JSON, duplicate members, or fails validation (including claim-level rules). |
| 2 | Content hash mismatch, malformed, or unsupported; or a signature invalid, malformed, unsupported, or errored. |
| 3 | `--strict` only: no content hash, a signature not checked, or no signature at all. |
| 64 | Usage error or unreadable key. |
| 70 | Internal error. |

## Conformance

`conformance/agent-work-receipt-v0.3-vectors.json` holds language-neutral
vectors, built from `fixtures/release-check.v0.3.json` by
`scripts/build-v0.3-vectors.mjs`:

- `validation_vectors`: an RFC 6902 patch (add, replace, remove) over a base
  receipt and the exact expected result: valid cases (including unchanged v0.1
  and v0.2 receipts) with their highest supported claim level, and invalid
  cases with every expected `{ path, code }` in the validator's order;
- `signature_vectors`: the signed payload, the RFC 8032 test public keys and a
  JWKS, and cases for a good signature, a wrong key, an unknown `kid`, a
  flipped signature byte, content changed after signing, and a changed
  protected header;
- `trace_commitment_vectors`: span sets and their `awr-trace-merkle/v1` roots.

The signing key is the published RFC 8032 test key; it is test material, not a
production key.
