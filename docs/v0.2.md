# Agent Work Receipt v0.2

v0.2 is v0.1 plus optional fields. Every v0.1 field keeps its meaning, a v0.1
receipt stays valid as v0.1, and a producer moves to v0.2 by changing
`schema_version` and adding only the fields it can fill honestly. The v0.2
schema is generated from the v0.1 schema (`scripts/build-v0.2-schema.mjs`), so
the shared parts cannot drift.

Each addition exists because a real producer had to hide it in `extensions`.
[trail](https://github.com/useorgx/trail) reads coding-agent transcripts and emits
one receipt per piece of work. Across 6,274 real receipts, these were the
questions v0.1 could not answer in core fields.

| Question a reader asks | v0.1 | v0.2 |
| --- | --- | --- |
| Which acceptance criterion did this check settle? | Criteria are plain strings; checks cannot point at them. | `intent.criteria[]` have ids; `verification.checks[].criterion_ids` point at them. |
| Was each criterion met? | Only one overall outcome. | `outcome.criteria_results[]`: `met`, `unmet`, `unknown` or `waived`, with evidence, a confidence, and who decided. |
| What range of results would have counted? | One sentence of intent. | `intent.expected_outcomes[]` (with optional `min`, `max`, `target`, `unit`) and `outcome.expected_results[]`. |
| Which values were seen, and which were guessed? | No distinction. | `provenance[]`: a JSON Pointer, a basis (`observed`, `declared`, `inferred`, `human`), a confidence, and the method and version. |
| Where did the approach change, and why? | Not representable. | `trajectory[]`: a change of course, retry, escalation, handoff, compaction, pause or resume, each with its trigger and evidence. |
| Which larger effort is this part of? | Only parent receipts. | `lineage.workstream_ref`; `lineage.references[].confidence` for links the producer inferred. |

## Rules the validator enforces

These rules are in addition to every v0.1 rule.

- Each `criteria_results[].criterion_id` must name a criterion in `intent.criteria`. There is at most one result per criterion.
- Each `verification.checks[].criterion_ids` entry must also name a criterion in `intent.criteria`.
- A `met` or `unmet` result needs evidence or a `decided_by` actor.
- An outcome of `succeeded` cannot sit beside an unmet **required** criterion. Use `partially_succeeded`. A criterion counts as required unless it sets `required: false`.
- Each `expected_results[].expected_id` must name an entry in `intent.expected_outcomes`. Where both are given, `min` must not exceed `max`.
- Each `provenance[].path` must resolve to a value inside the receipt.
- `trajectory[]` ids are unique, and their `action_ids` and `evidence_ids` resolve.
- Every confidence is a number in [0, 1]. Leaving it out means no claim.

## Recommended relationship vocabulary

`lineage.references[].relationship` stays producer-defined. Use these words
where they fit so hosts can join receipts without a mapping table:

- `produced_from`
- `continues`
- `retries`
- `supersedes`
- `depends_on`
- `reviews`
- `same_effort`
- `trace`

## Honest use

- **Leave fields out rather than fill them with guesses you would not stand behind.** An absent `criteria_results` makes no claim. A `status: "unknown"` result says the producer looked and could not tell.
- **Mark inferred values.** A producer that infers criteria from the request, or an outcome from the steps, should say so with `provenance`: `basis: "inferred"` and `method: "<rules or model>@<version>"`. A consumer can then weigh the value, or re-derive it with a better method.
- **Record a person's call as human.** When a person accepts or corrects a value, record it with `decided_by` or `basis: "human"`. Hosts should treat those values as ground truth and prefer them to any inference.
